# تدقيق المرحلة الأولى: سعة Hostinger قبل استضافة Supabase ذاتيًا

تاريخ التدقيق: 2026-08-18

النطاق: قراءة فقط لخادم التطبيق الحالي ولوحتي Hostinger وSupabase. لم تُغيّر إعدادات الخادم أو PM2 أو Docker أو الشبكة.

## نتيجة التدقيق والقرار التشغيلي

أوصى التدقيق الفني أولًا بفصل قاعدة البيانات في VPS مستقل، لأن الخادم الحالي يطابق تقريبًا الحد الأدنى الرسمي للحزمة الكاملة ويشغّل بالفعل سبع عمليات PM2 وخمس عشرة حاوية Docker وخدمات بيانات متعددة.

بعد عرض النتيجة، اعتمد مالك المشروع في 2026-08-18 تشغيل Supabase الذاتية على **الخادم الحالي نفسه** وعدم شراء VPS إضافي، مع شرط صريح بعدم إيقاف أو حذف أو تعطيل أي خدمة قائمة.

بناءً على ذلك، يتحول قرار المرحلة الثانية إلى تشغيل متوازٍ ومحكوم على الخادم الحالي، وليس قطعًا مباشرًا:

- استخدام منافذ وأسماء حاويات وvolumes وشبكة Docker جديدة لا تتعارض مع الموجود.
- ربط منافذ قاعدة البيانات والواجهات الإدارية بـ`127.0.0.1` فقط أثناء التجربة.
- تشغيل أقل مكونات Supabase التي يحتاجها المشروع، دون Storage أو imgproxy أو Edge Runtime أو Logs & Analytics.
- فرض حدود ذاكرة وإعادة تشغيل لكل حاوية ومراقبة الموارد بعد كل دفعة تشغيل.
- عدم إعادة تشغيل Docker أو PM2 أو Nginx Proxy Manager، وعدم تنفيذ `docker compose down` خارج مجلد الحزمة الجديدة.
- إيقاف التوسع فورًا إذا انخفضت الذاكرة المتاحة أو ظهرت زيادة في load أو إعادة تشغيل لأي خدمة قائمة.

| البند | النتيجة |

## أحمال Docker الحالية

- 15 حاوية نشطة من أصل 19.
- استهلاك الحاويات الظاهر وقت القياس يقارب 2.4 GiB.
- توجد بالفعل PostgreSQL 15 وPostgreSQL 16 وpgvector/PostgreSQL 16 وMySQL وRedis وQdrant وn8n وChatwoot وNocoDB وخدمات أخرى.
- صور Docker تستخدم نحو 10.72 GB، والـvolumes نحو 3.88 GB.

أكبر مستهلكي الذاكرة وقت القياس كانوا تقريبًا: n8n ‏480 MB، Chatwoot Sidekiq ‏403 MB، MySQL ‏373 MB، Chatwoot Rails ‏334 MB، وPostgreSQL الخاص بحزمة AI ‏222 MB.

## مقارنة بمتطلبات Supabase الذاتية

يوثق Supabase للحزمة الكاملة حدًا أدنى قدره 4 GB RAM و2 CPU و40 GB SSD، ويوصي بـ8 GB RAM أو أكثر و4 CPU أو أكثر و80 GB SSD أو أكثر.

الخادم الحالي يملك 2 CPU فقط، ويستهلك 3.5 GiB من ذاكرته قبل إضافة Supabase، ولا يملك Swap. لذلك لا يجوز اعتبار وجود 4.2 GiB متاحة مساحة آمنة للإنتاج؛ فهي تساوي تقريبًا الحد الأدنى النظري للحزمة قبل احتساب ذروة التطبيق والنسخ والاستعادة وذاكرة page cache.

المصدر الرسمي: <https://supabase.com/docs/guides/self-hosting/docker>

## نتيجة فحص الشبكة والأمان

- `ufw` غير مفعّل.
- لا توجد قواعد Hostinger Firewall.
- توجد خدمات تستمع محليًا على جميع الواجهات، من بينها منافذ إدارية وخدمات بيانات.
- الفحص الخارجي المقيّد للمنافذ المعروفة أثبت إمكانية الوصول إلى 22 و80 و81 و443 و8000 و8082 من الإنترنت وقت التدقيق.
- منافذ 5432 و5434 و5678 و6333 و6379 و8080 و8100 و9443 لم تكن قابلة للوصول من جهاز التدقيق وقتها، رغم ظهور بعضها مستمعًا داخل الخادم.

هذه النتيجة تمنع إضافة قاعدة إنتاج جديدة قبل تفعيل طبقة Firewall واضحة. لا يُفتح PostgreSQL على الإنترنت.

## مؤشرات Supabase Cloud الحالية

تعرض لوحة المنظمة وقت التدقيق:

- الخطة Free ومشروع واحد.
- 2 مستخدمين نشطين شهريًا.
- 6,068 رسالة Realtime في دورة الفوترة الحالية.
- 2.616 GB egress في دورة الفوترة الحالية.
- حجم قاعدة البيانات معروض كـ`0 / 0.5 GB`، والصفحة التفصيلية لم تعرض قياسًا دقيقًا لأنها اعتبرت أنه لا توجد مشاريع نشطة وقت القراءة.
- Storage معروض 0 GB، وهو متوافق مع عدم وجود استعمال فعلي لـSupabase Storage في الكود.

الحجم الدقيق للقاعدة يجب استخراجه في مرحلة النقل التجريبي من PostgreSQL نفسه أو من ملف dump، ولا يجوز الاعتماد على قيمة اللوحة المقربة.

## ضوابط استخدام الخادم الحالي

| البند | الضابط المعتمد |
|---|---|
| العزل | مشروع Docker مستقل وشبكة وvolumes وأسماء حاويات خاصة به |
| PostgreSQL | منفذ محلي غير متعارض أثناء التجربة، ولا يُنشر للعامة |
| API التجريبي | منفذ محلي جديد خلف reverse proxy عند اعتماد النطاق |
| الذاكرة | حدود صريحة للحاويات ومراقبة `free` و`docker stats` قبل وبعد التشغيل |
| الخدمات القائمة | ممنوع حذفها أو إيقافها أو إعادة إنشائها أو تعديل volumes الخاصة بها |
| المنافذ الحالية | ممنوع استخدام 5432 و5434 و8000 و8080 و8082 و8100 وغيرها من المنافذ القائمة |
| النسخ | نسخة مشفرة خارج الخادم قبل إدخال أي بيانات إنتاجية |
| الرجوع | إزالة حاويات المشروع الجديد وحدها، دون أوامر Docker واسعة النطاق |

لتقليل الاستهلاك في البداية:

- لا تُفعّل Logs & Analytics الاختيارية.
- أبقِ Auth وPostgREST وRealtime وPostgreSQL والـAPI gateway.
- احذف Storage وimgproxy وEdge Runtime من Compose بعد اختبار الاعتماد، لأن المشروع الحالي لا يستخدم Supabase Storage أو Edge Functions.
- اجعل Studio محميًا وغير متاح للعامة دون تحكم وصول.

## شروط بدء المرحلة الثانية

1. إنشاء حزمة Docker مستقلة بمنافذ محلية غير متعارضة وحدود موارد واضحة.
2. التحقق من الحزمة محليًا قبل نقلها إلى الخادم.
3. تشغيل مكونات البيانات الأساسية تدريجيًا ومراقبة الخدمات القائمة بعد كل خطوة.
4. اختيار نطاق فرعي للـAPI وRealtime قبل إتاحة البوابة عبر HTTPS.
5. اعتماد سياسة Firewall قبل فتح أي مسار جديد للعامة.
6. تحديد وجهة نسخ احتياطي خارج الخادم.
7. الاحتفاظ بقيم `AI_SETTINGS_ENCRYPTION_KEY` و`CRAWLER_SETTINGS_ENCRYPTION_KEY` الحالية، وعدم تدوير `SUPABASE_SERVICE_ROLE_KEY` القديم قبل اختبار فك التشفير وإعادة التشفير الآمن.
8. قياس حجم PostgreSQL الفعلي من المصدر وتجهيز dump تجريبي.

## ما لم يحدث في هذه المرحلة

- لم يُشتر VPS جديد ولم تُغيّر الخطة.
- لم يُثبت أو يُحدّث أي برنامج.
- لم تتوقف أي عملية PM2 أو حاوية.
- لم تُغيّر قواعد Firewall أو DNS.
- لم تُنقل بيانات ولم تُغيّر مفاتيح أو أسرار.
