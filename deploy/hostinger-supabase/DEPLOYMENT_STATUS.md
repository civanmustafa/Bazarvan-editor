# سجل نشر Supabase التجريبية على Hostinger

تاريخ التنفيذ: 2026-08-18

الحالة: النطاق الرئيسي يعمل الآن على Supabase الذاتي في خادم Hostinger الحالي، ولا توجد عملية محرر أو عامل نشطة تعتمد على Supabase Cloud. أزيلت عمليات النسخة القديمة من PM2، بينما بقي مشروع Cloud نفسه دون حذف.

## ما تم نشره

- الإصدار الرسمي المثبت: `self-hosted/v0.8.0`.
- مسار الخادم: `/opt/bazarvan-supabase`.
- الخدمات المشغلة فقط: PostgreSQL وAuth وPostgREST وRealtime وEnvoy.
- لم تُشغّل Studio أوStorage أوimgproxy أوEdge Runtime أوSupavisor أوLogs & Analytics.
- بوابة API مربوطة على `127.0.0.1:18000` فقط.
- أُضيف مسار HTTPS عام عبر الوكيل الموجود (Nginx Proxy Manager) على النطاق الحالي: `https://smarteditor.bazarvan.com/supabase/`، ويُمرّر عبر شبكة Docker الخاصة إلى `supabase-envoy:8000`.
- حُفظت كتلة المسار أيضًا في إعداد Nginx Proxy Manager المتقدم للمضيف (مع نسخة احتياطية من `database.sqlite`) حتى تبقى بعد إعادة توليد إعدادات الوكيل.
- بقي منفذ Envoy على المضيف `127.0.0.1:18000` للاستخدام المحلي، ولم يُفتح PostgreSQL للعامة.
- PostgreSQL لا ينشر المنفذ `5432` على المضيف.
- `SITE_URL` وredirect URL مضبوطتان على `https://smarteditor.bazarvan.com` استعدادًا للاختبار اللاحق.
- التسجيل العام وتسجيل الهاتف معطلان في البيئة التجريبية.
- حُوّل مضيف `smarteditor.bazarvan.com` نفسه إلى نسخة التطبيق المبنية في `/var/www/bazarvan-editor-staging` على المنفذ `8083`.
- بقي مجلد `/var/www/bazarvan-editor` وملف بيئته كأرشيف محلي فقط؛ لا توجد له عملية PM2 ولا يُستخدم في التشغيل.

## الإصدارات والحاويات

| الخدمة | الحاوية | الصورة | حد الذاكرة | حد CPU |
|---|---|---|---:|---:|
| PostgreSQL | `supabase-db` | `supabase/postgres:17.6.1.136` | 1280 MB | 0.80 |
| Auth | `supabase-auth` | `supabase/gotrue:v2.189.0` | 256 MB | 0.20 |
| PostgREST | `supabase-rest` | `postgrest/postgrest:v14.12` | 256 MB | 0.20 |
| Realtime | `realtime-dev.supabase-realtime` | `supabase/realtime:v2.102.3` | 512 MB | 0.40 |
| API gateway | `supabase-envoy` | `envoyproxy/envoy:v1.39.0` | 192 MB | 0.20 |

جميع الحاويات تستخدم سياسة إعادة التشغيل `unless-stopped`، وحدود PIDs وذاكرة swap مساوية لحد الذاكرة، حتى لا تزاحم الخدمات القائمة بلا سقف.

## نتيجة التحقق بعد التشغيل

- الحاويات الخمس: `running` و`healthy`، وعدد إعادة التشغيل لكل منها صفر.
- Auth عبر Envoy: HTTP 200.
- PostgREST عبر Envoy: HTTP 200 باستخدام فحص خادمي لا يطبع المفتاح.
- تم تطبيق جميع ترحيلات المشروع الـ75 على القاعدة التجريبية مع تسجيل checksum لكل ملف.
- تحقق مخطط المشروع: 45 جدولًا عامًا، 134 دالة عامة، 84 سياسة RLS، 44 trigger، وجدول واحد في publication باسم `supabase_realtime`.
- سجل الترحيل محفوظ في `/opt/bazarvan-supabase/backups/project-migrations-20260817T232714Z.log`.
- النسخة الاحتياطية السابقة للترحيل موجودة في `/opt/bazarvan-supabase/backups/pre-project-migrations-20260817T232714Z.dump` وتم اجتياز فحص SHA-256.
- فحص RPC للقراءة فقط (`current_user_role`) عبر PostgREST: HTTP 200.
- فحص Realtime: الحاوية `healthy`، وpublication تحتوي جدولًا عامًا واحدًا.
- فحص البوابة العامة بعد الإضافة: Auth HTTP 200، PostgREST HTTP 200، وRealtime WebSocket handshake HTTP 101. مسار Realtime الإداري `/api/tenants/.../health` يعيد `403 RBAC` عمدًا ولا يُستخدم كفحص عميل.
- أُنشئ حساب المدير `ciwan.mu90@gmail.com`، وأُكد بريده، وأصبح ملفه في `public.profiles` بدور `admin` وحالة نشطة.
- أُنشئت نسخة staging مستقلة في `/var/www/bazarvan-editor-staging`، وبُنيت الواجهة باتصال Supabase الذاتي دون تعديل `dist` الإنتاجي.
- خادم staging يعمل كعملية PM2 منفصلة باسم `bazarvan-editor-staging` على `8083`؛ أعاد `healthz` و`readyz` HTTP 200 وجميع فحوص الجاهزية ناجحة.
- اختُبر staging برمز مدير قصير العمر: Auth HTTP 200، RPC `current_user_role` أعاد `admin`، وRealtime WebSocket handshake HTTP 101.
- شُغّلت العمال الستة في smoke test قصير على قاعدة فارغة؛ لم يظهر خطأ قاتل أو متغير مفقود.
- بعد التحويل شُغّلت ستة عمال بأسماء `bazarvan-staging-*` بشكل دائم لخدمة قاعدة Supabase الجديدة، ثم أزيلت العمال السبعة القديمة من PM2.
- فحص النطاق الرئيسي بعد التحويل: `/healthz` و`/readyz` وواجهات الإدارة HTTP 200، Auth وREST HTTP 200، وRealtime WebSocket HTTP 101. حزمة الواجهة العامة تحتوي رابط Supabase الذاتي.
- تم اعتماد بداية نظيفة: لا توجد بيانات مقالات أو عملاء أو طوابير مستوردة إلى القاعدة الجديدة.
- كانت بروفة النقل معتمدة على مشروع Supabase Cloud، لكن لم تُنفّذ أي كتابة أو استعادة؛ لذلك لم تدخل بيانات Cloud في البداية النظيفة. ظهور Cloud بحالة `Unhealthy` لم يعد يؤثر على المحرر بعد إزالة العمليات القديمة.
- سجل Supabase يوضح أن العطل هو `HTTP 522` من API Gateway (انتهاء مهلة الوصول إلى origin) على طلبات مثل `/rest/v1/app_settings` وRPC الخاصة بالطوابير؛ لوحة المشروع أظهرت نجاحًا يقارب 12% وأخطاء API Gateway على معظم الطلبات، بينما لم تُظهر Postgres أخطاءً.
- لم يتم الضغط على Reset database password ولم تُغيّر مفاتيح الإنتاج، لأن ذلك قد يقطع الاتصالات والخدمات الحالية. يلزم عودة المصدر إلى حالة سليمة وتوفير كلمة مرور اتصال PostgreSQL (أو رابط اتصال مكافئ) قبل إعادة المحاولة.
- استهلاك الذاكرة الفعلي للحاويات الخمس وقت القياس: نحو 429 MB.
- الذاكرة المتاحة للنظام بعد التشغيل: نحو 3967 MiB.
- الحمل اللحظي بقي منخفضًا، والمساحة المتاحة على `/` نحو 67 GB.
- حاويات Docker السابقة: 15 من 15 بقيت تعمل؛ أصبح الإجمالي 20 بعد إضافة حاويات Supabase الخمس.
- أزيلت عمليات PM2 القديمة السبعة التي كانت متصلة بـSupabase Cloud (`bazarvan-editor` والعمال الستة التابعة لها).
- بعد الإلغاء تعمل عملية الويب الجديدة و6 عمال بأسماء `bazarvan-staging-*`؛ إجمالي عمليات PM2 أصبح 7، وكلها `online` من المسار الذاتي.
- حُفظت قائمة PM2 الجديدة عبر `pm2 save` حتى لا تعود عمليات Cloud بعد إعادة تشغيل الخادم.
- لم تُوقف أو تُحذف أي خدمة خارج عمليات المحرر القديمة. أُضيفت حاوية `supabase-envoy` فقط إلى شبكة `proxy` الخاصة بالوكيل، دون إعادة تشغيل الحاويات الأخرى.

## الأسرار والعزل

- وُلّدت مفاتيح مستقلة لهذه البيئة ودُوّرت قبل أول تشغيل للحاويات.
- ملف `/opt/bazarvan-supabase/.env` مضبوط بصلاحية `0600`.
- لا توجد قيمة سرية محفوظة في المستودع أو في هذا السجل.
- لم تُفتح قاعدة البيانات للعامة ولم تتغير قواعد DNS أوFirewall. أُضيف مسار Nginx Proxy Manager الخاص بـ`smarteditor` فقط، وأُعيد إعداد Nginx المضيف إلى نسخته الأصلية بعد التحقق.

## الحالة بعد الإلغاء الكامل

- النطاق الرئيسي متصل بـSupabase الذاتي، وفحوص `/healthz` و`/readyz` و`/api/healthz` وAuth تعيد HTTP 200.
- لا توجد أي عملية PM2 قديمة أو عامل نشط يستخدم `supabase.co`؛ قائمة الإقلاع المحفوظة تحتوي النسخة الذاتية فقط.
- لم تُنقل بيانات أو مستخدمون أو كلمات مرور؛ البداية نظيفة كما تم اعتمادها.
- نسخة `/var/www/bazarvan-editor-staging` هي النسخة العامة الفعالة للنطاق الرئيسي، ولا تستخدم مسارًا عامًا منفصلًا.
- مشروع Supabase Cloud لم يُحذف من الحساب، لكنه خارج مسار تشغيل المحرر. يمكن اتخاذ قرار حذفه لاحقًا بشكل منفصل بعد مراجعة أي تكامل خارجي مثل n8n.
- ملف `/var/www/bazarvan-editor/.env.production` القديم لا يُشغّل تلقائيًا؛ لا تستخدم المجلد القديم في أي نشر مستقبلي.

الخطوة التشغيلية المتبقية هي تسجيل الدخول بالحساب الإداري من النطاق الرئيسي وتشغيل smoke test وظيفي من المتصفح. لا تُعد تشغيل عمليات PM2 القديمة أو تستخدم ملف البيئة القديم.
